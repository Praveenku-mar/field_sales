# Architecture

## Overview
Field Sales is a Frappe v16 app (no ERPNext) for a brand's field reps: they check in at retail shops with GPS, take orders against live store stock, and the orders sync to the online store (Shopify today). Managers track visits, orders, sync health and sales-rep commission.
Backend: Python on Frappe (DocTypes, whitelisted APIs, RQ background jobs, scheduler). Frontend: a Vue 3 + frappe-ui SPA (Vite, Pinia, Tailwind) served at `/fieldsales` (alias `/fs`), plus standard Desk forms, reports and number cards.
Store access goes through a platform-neutral connector layer; only `connectors/shopify.py` and the `shopify/` package (App Store install, lifecycle and privacy webhooks) know Shopify (Admin GraphQL).

## Data flow
1. **Products & stock in:** scheduler → `sync/products.py → scheduled_sync()` (each enabled Store, `use_store`; one failure doesn't stop the rest) → `enqueue_sync(store)` (job id `sync_job_id(store)`) → `sync_products(store)` → `connector.get_products()` → Platform Product + Product Stock rows. Upsert, archive and the product/stock/price webhooks match only that store's products (Product Stock takes its product's store). Live stock on order: `sync/stock.py → fetch_live_stock()`. Store pushes `inventory_levels/update`, `products/update|delete` webhooks (step 5).
2. **Customers out:** Retailer `on_update` → `sync/customers.py → enqueue_push()` → `push_retailer()` → `connector.create_customer()` → `external_customer_id`.
3. **Visit:** rep checks in/out via `api/__init__.py → check_in() / check_out()` (GPS, geofence, own visit, visit date). Creating, reassigning or rescheduling a Visit notifies the rep (Notification Log).
4. **Order out:** Field Order `on_submit` → `sync/orders.py → enqueue_push_order()` → `push_order()` → `connector.create_order()` (Draft mode: draft order; Confirmed mode: real order). On an order id: `sync/orders.py → _assign_order_location()` (best effort, also in `link_completed_drafts()`) has `connector.assign_order_location()` commit its stock at the Field Order's `location_id` (Shopify: `fulfillmentOrderMove` of open fulfilment orders; scope `write_merchant_managed_fulfillment_orders`), then `commission/engine.py → enqueue_create_entries()` and `sync/confirmation.py → enqueue_order_confirmation()`. The store's draft number (e.g. #D5) is stored as `store_draft_name` (`shopify.py → _order_result()`; older drafts filled by patch `backfill_store_draft_names` via `connector.get_draft_names()`). Draft mode gets its order id later: at once from an order webhook (`sync/webhooks.py → _process_order_event()` → `sync/orders.py → link_order_from_event()`: `connector.field_order_from_order_event()` reads the Field Order No from the note Shopify copies from the draft, and `get_completed_drafts()` must confirm that draft became this order), else from `link_completed_drafts()` (cron); both use `_link_completed_draft()`, which locks the row so an order is linked (and confirmed) once (only drafts pushed in the last `DRAFT_LINK_DAYS` = 90 days, newest first, `DRAFT_LINK_BATCH` = 500 a run; a draft completed later is not linked automatically). Failures: `retry_failed_orders()` (cron), Sync Log, sync failure notifications to the rep's Sales Manager (orders) and System Administrator (customers).
5. **Webhooks in:** store → `api/webhooks.py → receive()` (HMAC verify, dedupe by delivery id in Redis, enqueue) → `sync/webhooks.py → process_event()` → stock/product updates or `commission/engine.py → reconcile_order()` for order created/paid/fulfilled/cancelled/refund (an unknown order is first linked to its Field Order's completed draft, `link_order_from_event()`). `OrderDetail.vue` reloads on `field_order_synced` and `field_order_payment_updated`. Stock events publish `stock_updated`; `products/update` applies payload prices (`connector.handle_product_event()` → `_apply_prices()`), re-fetches the product (`sync_one_product()`), then publishes `product_price_updated` `{product, price, compare_at_price}` for prices that changed (`_publish_price_changes()`). Both go to the Platform Product doctype room; the SPA listens via `composables/useRealtime.js`.
6. **Commission:** `reconcile_order()` re-reads the order (`connector.get_order()`) and sets entries to match the store's current state → monthly `commission/statements.py → generate_monthly_statements()` → Approve (submit) → `mark_paid()`.
7. **Emails:** order confirmation with invoice PDF (`sync/confirmation.py`), daily manager summary (`daily_summary.py`), Frappe Notifications; sent via the default outgoing Email Account.
8. **App Store install (OAuth mode):** embedded (default): Shopify managed install → admin loads `/fieldsales?shop=&host=&embedded=1&id_token=` → `www/fieldsales.py` → hook `field_sales_embedded_page` → `shopify/embedded.py → page_context()` → `ensure_offline_token()` (token exchange) → `oauth.py → save_installation()` → queued `register_webhooks()`; later API calls carry `Authorization: Bearer <id token>` → auth hook `session_token.py → authenticate()`. Non-embedded: `oauth.py → install()` → shop's `/admin/oauth/authorize` → `callback()` → `save_installation()` → redirect `/fieldsales`. Lifecycle/compliance webhooks → `shopify/webhooks.py → receive()` → `handle_uninstalled()` or `shopify/privacy.py → process()`.
9. Every store and Razorpay call writes a Sync Log (`sync_log.py → log_sync() / log_sync_durable()`).

**Visit import** – Excel/CSV bulk planning (Sales Manager/System Manager). `visit_import.py → download_visit_template(), preview_visit_import(), create_visits_from_import(), _check_import_access()`. UI: `components/VisitImport.vue` (Visits page, `?tab=import`).

**Orders** – order entry with stock checks, discount limit, tax. `doctype/field_order/field_order.py → FieldOrder` (`validate()`: whole quantities above 0 (`_validate_item_quantities()`), Active products only on draft save and submit (`_validate_products_for_sale()`); totals: discount first, then GST on the discounted value (`_compute_totals()`; the Desk form `field_order.js`, `OrderDetail.vue` and the mobile `FieldOrder` in `models.dart` compute the same way, and the GST invoice prints taxable value = net − discount); `_compute_item_amounts()` (rate = product price unless `PRICE_OVERRIDE_ROLES`), `_validate_amounts()` (tax 0–100, discount bounds), `_validate_discount()`, `before_submit() → _apply_live_stock()`, `on_submit()`, `before_cancel() → _settle_store_order_before_cancel()`; drafts start without items (`api/__init__.py → create_order()`, mandatory check skipped), so the page's Location picker saves through `set_order_location()` (same skip while the draft has no items), not `frappe.client.set_value`: refused while Pending; an open store draft is deleted (`connector.delete_draft()`, neutral contract, default no-op); a store order (or completed draft) must already be cancelled on the store, else the cancel is refused, as it is when the store can't be reached or the connection is off; `on_cancel()` then queues `enqueue_create_entries()` so commission follows the store's cancel); `sync/orders.py → push_order(), retry_failed_orders(), link_completed_drafts()`. **Order confirmation & invoice** – one email per order once it reaches the store, invoice PDF ("Tax Invoice" with GSTIN and CGST/SGST or IGST rows only when the company or retailer has a GSTIN, else "Invoice" with one Tax row), and a Razorpay Pay Now link when payments are enabled (see Payments). `sync/confirmation.py → send_order_confirmation(), resend_order_confirmation(), _build_pdf()` (60 s cap); print format "Field Sales Invoice" (fixture); company details on the Store (Invoice section). **Store context and isolation (multi-merchant)** – `utils/store.py`: `get_store_name(store=None)` = the given store, else the current one (`set_current_store()` / `use_store()`), else the session user's own store (`user_store()`), else the site's only Store (cached per request; `NoStoreContext` when several exist and none is set). Reads/writes go through `get_store()`, `get_store_value()`, `set_store_value()`, `get_store_password()`; `get_connector(store=None)` builds the connector from that Store and the token-refresh lock is per shop. Single-store sites keep their old series. Patch `v2_0/create_first_store` (also run by `install.after_install`) turns Store Connection into the first Store and fills `store` everywhere. Design and remaining phases: `docs/multi-merchant/design.md`. **One user = one store:** `assign_user_to_store()` gives the user a default User Permission on Store (applies to every doctype, so Frappe filters lists/forms/REST too); done by `Sales Rep.on_update`, `Retailer.on_update` and `shopify/embedded.py → get_embedded_user()` (one embedded user per store on the shared site: `embedded_email()`). `store_scope(user)` = `None` vendor staff (System Manager with no store: all stores) / a store code / `""` nothing (shared site, user in no store); on a single-store site a user without a permission belongs to its only Store. `permissions.py` applies the store first in every `*_query`, `*_has_permission`, `scope_criterion` and `hierarchy_filters` (so also for admins), with store-only hooks for Platform Product, Product Stock, Sync Log, Commission Plan and Privacy Request; `api/mobile.py → _execute_keyset_query()` adds the store to every raw-SQL list. A new record takes its rep's store (`stamp_store`, `_in_store`) and a user cannot create one for another store. `sync/notify.py → users_with_roles(roles, store, vendor=)` lists only that store's users (alerts never cross stores). **Requests and jobs without a store user:** `enqueue_in_store(method, store=, **kw)` queues `run_in_store`, which runs the job under `use_store()` (record jobs pass `record_store(doctype, name)`: push order, mark paid, confirmation, commission, push retailer; customer import job id per store). Scheduled jobs call `for_each_store(fn, title, enabled_only, filters)` (a savepoint per store: a failure undoes only that store's work, is logged and the next store runs; it commits only when a store failed, then fails the job so the Scheduled Job Log shows it; tests calling a job stay rolled back): order retries, draft linker, store payments, shop settings (`daily_sync`), and, also for disabled Stores, anonymise, statements and the daily summary (not for uninstalled ones). `products.scheduled_sync` has its own per-store loop. `reconcile_open_links` and `clear_old_logs` stay site-wide (Razorpay is off on the shared site). `shop_store(shop)` = the shop's Store, else the site's Store on a single-store site, else `None`: used by store webhooks (`api/webhooks.py`, `X-Shopify-Shop-Domain`, HMAC then checked with that Store's keys), app webhooks (`shopify/webhooks.py`: uninstall disables only that shop's Store; the Privacy Request gets it), session token (`session_token._connection(shop)`, `authenticate` sets the current store), `embedded.is_connected` / `page_context`, and OAuth (`check_shop_allowed`, `save_installation` creates a new Store for a new shop on the shared site). Logs for a shop with no Store go to Error Log (`sync_log.log_sync_or_error`). The Razorpay webhook answers 404 on the shared site. **Vendor staff in the app (shared site, Phase 7):** they work in one store per browser session: `utils/store.py → vendor_store()` / `set_vendor_store()` (cache `field_sales:vendor_store:{sid}`, 24 h), read by `get_store_name()` and by `store_scope()` for the session's own user, so lists, forms and reports show that store only. `frontend_api.get_vendor_stores` / `switch_store` (vendor + shared site only; each switch comments on the Store). `get_session` works without a store (`store: {}`, `is_vendor`), and `App.vue` shows `VendorStorePicker.vue` until one is picked; the user menu has Switch store. - **Shopify webhooks** → `/api/method/field_sales.api.webhooks.receive`; topics `inventory_levels/update`, `products/update`, `products/delete`, `orders/create` (links a completed draft at once, even when the payment is manual/COD and no `orders/paid` follows), `orders/paid`, `orders/fulfilled`, `orders/cancelled`, `refunds/create` (declared in `shopify.app.toml` for App Store installs, and also subscribed through the API by `shopify/webhooks.py → register_webhooks()` (`STORE_API_TOPICS` → `config.STORE_WEBHOOK_PATH` at `shopify_app_url`; rerun it after the public address changes); otherwise created outside the app). App webhooks → `/api/method/field_sales.shopify.webhooks.receive`: `app/uninstalled` (registered by `register_webhooks()`), compliance topics (toml only; Shopify can't register them by API).
- **Customer and order addresses**: `connectors/shopify.py → _person_name()` sends the owner's (else the shop's) name as first/last name, split at the last space; Shopify's checkout rejects a shipping address with no last name.
- **Order metafields** (app-owned, namespace `$app:field_sales`): `field_order_no`, `sales_rep`; definitions created by `connectors/shopify.py → ensure_order_metafields()`.
- **WooCommerce / Odoo connectors** – separated into companion apps (`field_sales_woocommerce`, `field_sales_odoo`) that register with Field Sales via the `field_sales_connectors` hook. Store credentials and platform-neutral sync routines remain in core.
- **Razorpay REST API** (India only: its payload keeps `payments/razorpay.py → indian_phone()` for the customer contact) `https://api.razorpay.com/v1`, basic auth with Razorpay Settings `key_id` / `key_secret`. Mode (Test/Live) is display-only: the key decides it. Webhook → `/api/method/field_sales.payments.razorpay.webhook` (events `payment_link.paid|partially_paid|expired|cancelled`), signed with `webhook_secret` (not the key secret). Razorpay stores the URL entered in its Dashboard; it must be public HTTPS (a tunnel for local sites; don't set `host_name` to it, see Gotchas).
- **Email** – Frappe default outgoing Email Account (configured in Settings → Email).
- **PDF** – wkhtmltopdf via Frappe (`frappe.utils.pdf.get_pdf`).
- **Camera** – `html5-qrcode` (npm) in the SPA; uses the browser's BarcodeDetector when available.
- **Maps** – Leaflet in the SPA (`components/MapEmbed.vue`, `MapPickerDialog.vue`); tiles from OpenStreetMap, place search via OSM Nominatim (`MapPickerDialog.vue`).
- **Env vars / secrets**: none read from the environment; credentials live on the Store and in Razorpay Settings (Password fields, read only with `get_password()`), except the Shopify App Store app's, which are site_config keys (`shopify/config.py`). `frappe.conf.developer_mode` affects the SPA shell. Site config `host_name` must be reachable locally (see Gotchas).

## Conventions
- Python: tabs, docstrings on public functions, `_()` for user-facing text, type annotations on all whitelisted methods (`require_type_annotated_api_methods = True`).
- Store-specific code only in `connectors/`; callers use neutral shapes documented in `connectors/base.py`. Platform ids are stored plain (no `gid://`).
- Store failures raise `ConnectorError(message, code, http_status, details, partial)`; sync jobs catch it, mark the record Failed, write Sync Log, and do not re-raise; other exceptions are re-raised after logging.
- Background work: `frappe.enqueue(..., enqueue_after_commit=True, job_id=..., deduplicate=True)`. Never pass `event=` as a job kwarg (reserved by `frappe.enqueue`).
- Permissions: rep-scoped DocTypes use `permissions.REP_FIELD` + hooks `permission_query_conditions` / `has_permission`; Payment Transaction follows its order's rep (`reference_order`, else `store_order_id` = Field Order `external_order_id`; `payment_transaction_query` / `_has_permission`); manager actions check Sales Manager / System Manager. Gotcha: `has_permission` sees the record as sent, and `frappe.client.save` / desk `savedocs` never check the stored one, so `permissions.check_owner_change` (doc_events `validate`) refuses moving a record whose stored `sales_rep` is outside the user's hierarchy. Every rule works inside the user's store first (`store_scope()`): a Store Admin or System Manager that belongs to a store sees only it.
- Roles: System Manager (vendor staff when in no store), Store Admin (the merchant owner: System Manager inside one store; role sets `ADMIN_ROLES` / `MANAGER_ROLES` / `STAFF_ROLES` live only in `permissions.py`, import them). Gotcha: `is_admin()` is true for Store Admin, so anything vendor-only (changing a Sales Rep's user, Store `VENDOR_ONLY_FIELDS` such as `embedded_user` and credentials: `store.py → _guard_vendor_fields()` via `utils/store.py → can_change_connection()`, which also lets a single-store site's own System Managers through even when they are assigned to its store) must check `is_vendor()`; the embedded user must pass `can_be_embedded_user(user, store)` (never Administrator, vendor staff or another store's user), checked on Store save and again at sign-in (`embedded.get_embedded_user`); `assign_users_to_store` skips System Managers, and code that skips the hierarchy for admins with `frappe.get_all` must still filter by `store_scope()` (both reports do), Sales Manager, Field Sales Rep; Field Sales Retailer is the customer login (My Orders only, no desk).
- Frontend: frappe-ui components, `PageHeader`, `SectionCard`, `DataTable` (page-size footer), `StatusPill`, `NumberCard`, `EmptyState`; page tabs kept in `?tab=`; nav in `utils/nav.js`. Only Tailwind classes present in the frappe-ui 1.0 build (e.g. no `bg-surface-white`).
- Tests: `field_sales/tests/test_*.py`, `frappe.tests.IntegrationTestCase`, store mocked by patching connector methods; per-test rollback in `tearDown` (class-level rollback only otherwise).

## Gotchas
- Notification templates (`notification/*/`: the `.html` and the JSON `message`, kept identical) escape user and store text with `| e` (retailer name, rep, sync error). `bench migrate` reloads a standard Notification only when its JSON `modified` is newer than the database copy: bump it after editing.
- Per-store settings are on Store, not Store Connection: read them with `utils/store.py` helpers, never `get_single_value("Store Connection", ...)` (only `failed_log_retention_days` / `plan_limits` remain there). With several Stores, any code path without a current store raises `NoStoreContext`: queue jobs with `enqueue_in_store()` (never bare `frappe.enqueue` for store work), loop scheduled jobs with `for_each_store()`, and filter their queries with `store_filters()` / `store_criterion()`.
- Commission is state-based: replayed or out-of-order webhooks are safe; entries on Approved/Paid statements are never edited — corrections become negative Adjustments (so Unpaid can go below zero).
- Commission entries keep the rate they were created with; editing a plan doesn't change existing entries. Tiered Slab rates are provisional until the statement is built.
- Field Order tax is calculated before the discount (invoice prints the Field Order's own amounts). TODO: verify with accounting whether tax should follow the discount.
- Shopify orders and drafts carry no location: Shopify's routing assigns one (the default location unless Order routing says otherwise), so without `assign_order_location()` the stock of an order sold "at" another location is committed at the default one (it goes negative there). A draft's checkout link counts only stock at locations in a shipping profile ("shipping origins", `Location.shipsInventory`) and offers only countries in the store's Markets, so a location that is "Sell from here" in Field Sales but not a shipping origin makes the checkout say Sold out. Both are store settings the app cannot change (no shipping scope).
- A background job runs as the user who queued it (`frappe.enqueue` records `frappe.session.user` at the call). Webhook deliveries are accepted as Guest, so their jobs switch to Administrator first (`sync/webhooks.py → process_event()`, `payments/razorpay.py → _as_administrator()`); otherwise anything they queue, such as the order confirmation (which prints the invoice), fails with a PermissionError.
- Server dates and times are naive values in the site's time zone (System Settings, the store's when its settings are matched). The SPA gets it as `window.time_zone` (`www/fieldsales.py → get_boot()`, read with `get_system_timezone()`: the defaults copy can lag) and uses the site clock for anything compared with now: `utils/format.js → siteNow(), today(), nowSql(), isPast(), msUntil(), daysAgo()`; `toDate()` reads a bare date as a calendar date (JS parses "YYYY-MM-DD" as UTC midnight, the previous day west of UTC). Only the Dashboard greeting uses the viewer's clock.
- The companion editions (`field_sales_woocommerce`, `field_sales_odoo`) keep their own copy of the SPA and of `api/dashboard.py`; a page or period added here is not in them until copied (Last Month and the 2026-11 review fixes F7–F12, the draft location switch, the site time zone and the webhook user reached them on 2026-11-19; their shared test is `tests/test_review_fixes.py`). Each edition has its own test site (`fieldsales-woo-test.localhost`, `fieldsales-odoo-test.localhost`): they define the same DocTypes, so they cannot share one. Their SPA has no root `package.json`, so `bench build --app <edition>` does not rebuild it: run `yarn build` in the edition's `frontend/`.
- Draft mode: the store order (and commission, confirmation email, metafields) only exists once the draft is completed; Shopify doesn't copy draft metafields to the order, so `link_completed_drafts()` sets them. It also carries the payment across (`_carry_draft_payment()`): a draft paid on the store's checkout (any gateway, e.g. Razorpay on Shopify) had its paid webhook ignored before the link, so `apply_store_payment()` runs then; a draft already paid in Agamsale queues `enqueue_mark_store_paid()` (off on App Store installs).
- Retry de-duplication finds an existing order by `source_identifier` (Field Order name), falling back to the legacy `field-order-<name>` tag. In Draft mode a retry without a stored draft id (the first attempt's response was lost) looks for the customer's `field-sales` drafts and reuses the one whose Field Order No metafield (or older note) matches (`shopify.py → _find_draft()`, only when `sync_attempts > 1`).
- PDF generation fetches print CSS from the site's `host_name`; a public/unreachable `host_name` (e.g. a tunnel URL) makes wkhtmltopdf hang — capped at 60 s in `sync/confirmation.py`.
- Shopify requests use a (5 s connect, 30 s read) timeout; a broken IPv6 route otherwise stalls each call.
- Webhook signatures are verified with the app's client secret; webhooks created in Shopify admin may use a different key and fail verification.
- The SPA's only realtime use is `composables/useRealtime.js → onDoctypeEvent()` (Order Detail: live price/stock); sidebar counts still poll every 60 s and some pages poll for job results. The socket goes to `hostname:socketio_port` when `dev_server` (boot values from `www/fieldsales.py → get_boot()`), else the page origin — production needs nginx proxying `/socket.io`; a tunnel to the dev server gets no realtime.
- Field Order Item `rate` is sent to the store as the line price, so for non-managers the server sets it to the product's current price on save (read-only is only a UI hint; REST could set it) — except a saved row whose product and rate are unchanged (`get_doc_before_save()`), so a rep's save keeps a manager's rate and the price the draft was made at. An amended order's rows are new rows, so they get current prices.
- Price webhooks never change `rate` on order rows: draft rows show "Price changed" (`OrderDetail.vue → priceChange()`) with Apply (for a rep, any rate change becomes the product's current price, which is the same thing); the announced price is the one stored after the re-fetch, so out-of-order deliveries can't announce a stale price.
- Geofence can't be moved by reps: a located Retailer's latitude/longitude and any `geofence_radius_m` are manager-only (`retailer.py → _guard_location()`; reps may set the first location; check-in sets it via `frappe.db.set_value` only for the visit's own retailer, only while empty, and only from a fix ≤ `LOCATION_FILL_MAX_ACCURACY_M` (100 m), else warns). The geofence uses distance only, never the reported accuracy. A checked-in Visit keeps the retailer position it was measured against (`visit.py → _guard_check_in_fields()`, `RETAILER_POSITION_FIELDS`); without that, the read-only `fetch_from` re-fetches the Retailer's current position on every save and recomputes the distance.
- Check-in only on the visit's date (system time zone) and only by the assigned rep; check-out is not date-limited and managers may check out a rep's visit.
- Excel import is manager-only and re-validates every row server-side on create; uploads are private and deleted after a successful import.
- Notification Log "Alert" type is delivered even to the sender, so `Visit._notify_rep()` skips self-assignments itself.
- Camera (barcode scan) and GPS only work in a secure context: HTTPS or `localhost`. Plain `http://<LAN-IP>` on a phone shows "Camera not available".
- Browser Clipboard API also needs a secure context; `frontend/src/utils/clipboard.js` falls back to selection copying on local HTTP, and `OrderDetail.vue` shows a selectable link if the browser blocks both methods.
- Print formats render with wkhtmltopdf (old WebKit): no flexbox/grid — lay out with tables; colours need `-webkit-print-color-adjust: exact` (see "Field Sales Order" in `fixtures/print_format.json`). Fixtures only re-sync when their `modified` is newer than the site's.
- Mobile app sign-in (`api/__init__.py → mobile_login()`, returns API key/secret) must apply Frappe's `/login` rules itself, since it never builds a `LoginManager` session: "Disable Username/Password Login", Restrict IP (`frappe.auth.validate_ip_address`), login hours and password expiry (`LoginManager.validate_hour` / `force_user_to_reset_password` on `_MobileLoginAttempt`), Frappe's login-attempt trackers (`_frappe_login_trackers()`) plus the app's own 5-try lockout, and 2FA in two calls: `usr`+`pwd` → `{"message": "Verification", "tmp_id"}`, then `otp`+`tmp_id` → keys (Frappe's cached `tmp_id` keys, deleted once used).
- `create_sales_rep()` can link any existing User, so rep-scoped actions on the *user* must check that user's roles: `_check_password_target()` lets non-System Managers reset only users whose roles are within `REP_ONLY_ROLES` (Field Sales Rep + automatic roles).
- Frappe only sends system email through an Email Account that is enabled **and** default outgoing (or site config `mail_server`); an enabled non-default account is not enough. Check with `EmailAccount.find_default_outgoing()`.
- Field Order Item `available_qty` is always the server's stored stock at the order's location (`_set_row_stock()`, on draft saves *and* the submit save), never the client's; don't set it from Platform Product, which holds only the default location's stock and would also undo `_apply_live_stock()`.
- Store ids and sync state on Field Order (`SYNC_FIELDS`) and Retailer (`SERVER_FIELDS`) are server-only: `validate()` undoes client changes (`utils/guards.py → keep_server_fields()`; new and duplicated docs start clean; System Managers may correct saved ones). Sync code must write them with `db_set` / `frappe.db.set_value`, or save with `flags.ignore_sync` (Retailer). `location_id` is deliberately not guarded: it is the user's pick, checked by `_validate_location()`. Field Order has no `amended_from`, so cancelled orders are redone by Duplicate. Payment fields (`field_order.py → PAYMENT_FIELDS`) are guarded for everyone, System Managers included, in `validate()` **and** `before_update_after_submit()` (they are allow_on_submit, and validate does not run on Update after submit); payment code must `db_set` them.
- Push devices (`push/devices.py → register()`, Mobile Device, one row per Firebase token): a token already registered to another user moves only when that owner is disabled or unseen for `HANDOVER_AFTER` (1 day: the row's `last_seen` or User `last_active`). While the owner is active, register turns pushes to it off, sets `handover_to` and returns `handover_pending`; the owner's next register (or Profile switch) turns them back on. Knowing a token must never be enough to receive someone's notifications.
- `client_temp_id` is backed by a unique hidden `client_temp_key` so concurrent inserts block and fail rather than duplicate; cancelling frees it (Field Order `on_cancel` blanks the key; Visit blanks it when `status == "Cancelled"`), so the id may be reused. The key is set on insert (and when a Visit is un-cancelled), never recomputed on later saves: duplicates made before it existed are left keyless by patch `client_temp_key` and must stay savable. `push_order()` re-checks `docstatus` under a row lock right after `create_order` and marks the order Failed with `CANCELLED_DURING_PUSH` if it was cancelled while being sent, keeping store ids so the store order can be found and cancelled.
- Razorpay `reference_id` must be unique per link, so a replacement link for an order uses NAME-2, NAME-3 (next after the stored link's reference; a taken id moves on). Expiry is stored in the system time zone from Razorpay's `expire_by` (`_from_unix()`); `link_expiry_hours = 0` means no expiry. If creating fails after the old link was cancelled, the order is committed as Link Cancelled before the error. New Link's cancel of the old link comes back as a `payment_link.cancelled` webhook that can find the order by the old id and then wait for the row lock while the new link is saved; `webhook()` re-checks `_stale_link()` after locking and records it Ignored (otherwise the new link shows Link Cancelled).
- A DocType field can't be named `field_order` (clashes with the DocType's own `field_order` layout; migrate fails in `Meta.sort_fields`) — links to Field Order from new doctypes use another name (e.g. `reference_order`).
- Match Store Currency and Timezone overwrites System Settings `currency` / `time_zone` daily; to keep a different site value, turn it off (the store's values are still saved and reported as a mismatch). Visit dates and schedules then follow the store's time zone. All money text uses the site currency: Python via `utils/money.py → site_currency()` (confirmation email, Razorpay payload/comments/notifications, cancel message), SPA via `utils/format.js → formatCurrency()` (boot `sysdefaults.currency`), Desk via `frappe.defaults.get_default("currency")`; never hardcode INR. Commission Entry/Statement `currency` is copied from the store order (`engine.py`), so entries made while the store had another currency keep it.
- Guest GET endpoints (OAuth install/callback) are not auto-committed by Frappe (only unsafe methods are): `oauth.py` commits itself. Tests patch `frappe.db.commit`/`rollback`, since the token refresh and the endpoints commit.
- `frappe.db.get_value("Singles", ...)` fails (adds `ORDER BY creation`); read raw Single values with `frappe.qb` (`connectors/shopify.py → _stored_datetime()`). A worker's earlier reads pin a REPEATABLE READ snapshot, which is why `_refresh_oauth_token()` commits before re-reading tokens.
- Float columns (Retailer/Visit latitude/longitude) are NOT NULL: "no location" is 0, so redaction writes 0, not None.
- Shopify retires every other token when one is issued (install or refresh), so refresh runs under one Redis lock and a reinstall replaces both tokens; an `app/uninstalled` job older than the latest install is ignored.
- Embedded (Shopify admin iframe): no Frappe cookies (SameSite=Lax sid is not sent to a third-party iframe) and no usable local/session storage in Chrome incognito. Bearer requests therefore skip Frappe's CSRF check (it only applies when a cookie session holds a token). Socket.io can't sign in: `useRealtime.js` polls `onDocEvent` every 30 s and skips `onDoctypeEvent`. Desk links (`/app/...`, `documentTarget()` hrefs) don't work there. Location and camera are blocked in the admin's iframe (no `allow=` from Shopify): `utils/api.js → getPosition()` says so; scan buttons and Use My Location are hidden, and `VisitDetail.vue` swaps Check In / Check Out for "Open in Field Sales" (`shopify/embedded.js → openStandalone()`: same path in a new tab, standalone login). Never redirect to `/login` in embedded mode (it would bounce between admin and standalone).
- site_config changes (e.g. `shopify_app_*`) are only seen by a running web process after a restart / reload.
- bench's nginx template adds `X-Frame-Options: SAMEORIGIN` to every response; Python can't remove it. Browsers ignore it when CSP `frame-ancestors` is present (embedded page), but drop it for `/fieldsales` in production nginx if review flags it.
- Shopify App Pricing sends no subscription webhooks after April 28, 2026 (no `app_subscriptions/update`); the plan is read from the Partner API, and plan changes arrive as `plan_handle` on the welcome-link redirect.
- Frappe writes Access Log rows with a deferred (Redis) insert outside tests: they appear after the queue flushes, and tests should patch `make_access_log` rather than count rows.
- `sync/notify.py → users_with_roles()` caches per request/job in `frappe.local`; tests that add role users must clear `frappe.local.field_sales_role_users`.
- No `before_request` hook sets the store: API-key (mobile) and Shopify session-token auth run after Frappe's `init_request`, so the session user is still Guest there. The store is resolved lazily by `get_store_name()` from the session user instead. Guest entry points (webhooks, session token, install) set it from the shop (`shop_store()` → `set_current_store()`); jobs carry it (`enqueue_in_store`). Not a `before_job` hook: Frappe retries a deadlocked job with the same, already-popped kwargs.
- A Frappe User Permission on Store also limits the Store doctype itself and every Link to it; `frappe.get_all`, `frappe.qb`, `frappe.db.*` and `ignore_permissions` code ignore it, so those need an explicit store (`store_filters()`, `store_criterion()`, `scope_criterion()`).
